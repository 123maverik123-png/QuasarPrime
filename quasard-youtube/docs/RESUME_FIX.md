# «Алиса, продолжай»: почему не работало и что исправлено

Разбор по логам 27.10.2026 (`C:\quasard-main\data\server.log`,
`C:\workspace\quasard-youtube\logs\serve.log`). Проверено на живой Станции
Lite 2 (`L01Q9S4000AN4V`, 192.168.50.104).

## Что происходило на самом деле

«Пауза» работала, «продолжай» — нет. Цепочка **не рвалась** на распознавании:

```
20:33:43,495 INFO uniproxy: ASR: 'Продолжай.'
20:33:43,499 INFO httpx: GET  http://127.0.0.1:8099/api/status 200
20:33:43,501 INFO httpx: POST http://127.0.0.1:8099/api/resume 200
20:33:43,501 INFO uniproxy: YouTube: команда resume
```

ASR распознал, `intents.match_youtube` вернул `resume`, `active()` дал `True`,
мост ответил `200` и отправил `audio_play` с `offset_ms`. Обрыв был дальше —
**Станция не переоткрыла поток**, а мост считал попытку успешной и больше
ничего не делал:

```
20:33:43 service: Продолжение с 105311 мс (байт 4829855/6888000, пауза=True, простой 49.1 c)
20:33:43 glagol:  audio_play -> .../3YfklKRs...mp3      <-- команда ушла
20:33:46 streaming: Станция закрыла поток досрочно (4829855/6888000 байт)
20:33:46 streaming: старое соединение закрыто после resume (epoch 1 -> 2)
                                                         <-- и тишина: Range не пришёл
```

## Четыре независимые причины

### 1. «Мёртвое» состояние сессии после неудачного resume

`resume()` снимал флаг `session.paused` **до** того, как Станция реально
подключалась, а обработчик потока при выходе видел смену `resume_epoch` и
ранний `return` — то есть тоже не выставлял `paused`. Итог: `paused=False`,
`connected=False`, `finished=False`. Следующие «продолжай» попадали в условие
`(paused or stalled)` = ложь и уходили в ветку

```python
if send_command:
    await self.glagol.resume()      # {"command": "play"}
```

то есть в транспортную команду Glagol, которая с audio_client-сессией **ничего
не делает**. В логе это видно как `Glagol: play (продолжение)` два раза подряд
(20:33:49 и 20:33:56) при полной тишине. Каждое повторное «продолжай» было
гарантированно пустым.

### 2. Эхо-кадр кольца отменял продолжение

`RING_MUTE_S = 4.0` защищал от эхо-кадра `PlayerContinueSemanticFrame`, но флаг
`_ring_mute_until` лежал **на объекте `UniproxySession`**, а Станция присылает
эхо уже в **новом** WebSocket-соединении (в логе каждый кадр идёт сразу после
«WS подключение»). Окно не срабатывало:

```
20:22:56,255 POST /api/resume        <-- голосовое «продолжай»
20:22:56,345 Кольцо: кадр=['PlayerContinueSemanticFrame'] -> 'toggle'
20:22:56,353 Кольцо: переключатель -> pause (paused=False, state=streaming)
20:22:56,355 POST /api/pause         <-- продолжение отменено через 0.1 c
```

### 3. `offset_ms` уезжал вперёд от повторной паузы

`pause()` каждый раз пересчитывал позицию по настенным часам, а Станция в
паузе уже ничего не читает:

```
20:33:17 Пауза на 4829855 байт (позиция 97405 мс)
20:33:25 Пауза на 4829855 байт (позиция 105311 мс)   <-- +8 c из воздуха
```

### 4. Прошивка игнорирует `audio_play`, пока держит старый сокет

Самое важное. `stop` и `audio_play` уходили в одну и ту же секунду, а Станция
ещё 5 секунд держала старый HTTP-поток и новую ссылку не открывала:

```
21:24:17 service: Продолжение: полное переподключение с 8062 мс
21:24:17 glagol:  stop
21:24:17 glagol:  audio_play -> .../eeWXmymd...mp3     <-- та же секунда
21:24:22 streaming: Станция закрыла поток досрочно     <-- только теперь
                                                        <-- Range так и не пришёл
```

Когда Станция успевала закрыть поток раньше команды (21:21:39, 21:27:04), всё
работало с первой попытки. Отсюда вывод: **между `stop` и `audio_play` надо
дождаться освобождения сокета**, а не надеяться на тайминг.

## Что теперь делает мост

`POST /api/resume` принимает `{"send_command": bool, "force": bool}` и работает
как лестница:

1. **Поток жив и Станция его читает** (`connected` + отставание
   `behind_s() <= 3 c`) — ничего не делаем. `behind_s()` вместо `stalled_for()`:
   Станция забирает звук рывками на минуты вперёд и потом молчит в сокете, это
   нормальное воспроизведение, а не пауза.
2. **Поток завершён** — трек включается заново.
3. **Поток висит** (пауза / `connected=False` / отстала > 3 c):
   - `stop`;
   - `release_stream()` — снимаем свой HTTP-handler, чтобы сокет освободился
     детерминированно, а не «когда прошивка соизволит»;
   - ждём освобождения (до 2 c) и 0.2 c на перестройку плеера;
   - `audio_play` с `offset_ms` и **новым url** (`/stream/<новый токен>.mp3` —
     тот же буфер, та же сессия; прошивка не узнаёт старую ссылку и не
     игнорирует команду);
   - ждём новый `GET /stream/...` до `resume_connect_timeout` (4 c);
   - не вышло — повтор (всего `resume_attempts = 2`), каждый раз с новым url;
   - не вышло и это — трек перезапускается целиком (`resume_escalate_play`):
     лучше музыка с начала, чем тишина.

`send_command` оставлен для совместимости, но `{"command":"play"}` больше не
отправляется никогда — он и был тем самым «пустым действием».

## Что изменено в quasard

* `Services` хранит окно «не верить кадру кольца» на устройство
  (`ring_mute_until` / `ring_mute_why`), а не на соединение.
* `_youtube_command`: `player_pause` / `player_continue` уходят в VinsResponse
  сразу, а команда мосту — в фоне через `_spawn_background` (задачи сессии
  отменяются вместе с WS, который Станция закрывает через ~1 c после ASR).
* «Продолжай» гейтится `active_or_resumable()`: после паузы Станция может
  закрыть поток, и активной сессии уже нет, хотя продолжать есть что.
* `YoutubeControl.resume(force=...)`, таймаут `youtube.resume_timeout_s = 25`.
* `intents._RESUME` расширен (падежи объектов, «давай дальше», «можешь
  продолжить», «снять паузу»), лимит слов в `match_youtube` поднят с 5 до 8,
  чтобы «продолжай воспроизведение песни с того же места» не улетало в LLM.

## Как проверять дальше

Успешное продолжение в `logs/serve.log`:

```
Продолжение 1/2: переподключение с 10069 мс (байт 1619427/4968000, причина: paused)
Glagol: stop
HTTP: старое соединение закрыто после resume (epoch 0 -> 1)
Glagol: audio_play -> http://192.168.50.95:8099/stream/<НОВЫЙ токен>.mp3
HTTP: запрос потока token=... Range='bytes=234520-...' -> start=234520, статус=206
Продолжение принято: Станция снова читает поток
```

`start` в `Range` ≈ `offset_ms / 1000 * 24000` — это и есть «с того же места».

Тревожные признаки:

| В логе | Значение |
| --- | --- |
| `Продолжение 1/2` … но нет `HTTP: запрос потока` | прошивка не приняла `audio_play`; смотрите вторую попытку |
| `Станция не открыла поток` дважды + `Перезапускаю трек целиком` | продолжение не поддержано, но музыка вернулась с начала |
| `Продолжение не нужно: поток жив` | вы пришли, когда уже играло |
| `YouTube: мост переподключил поток с N мс` в `server.log` quasard | всё прошло штатно |

## Откат

Резервные копии quasard: `alice_server\<файл>.bak-20261027-211927`.
Мост: правки в `quasard_youtube/{service,streaming,glagol,config}.py`, поведение
возвращается установкой `pause_command = true` (жёсткий `stop`: продолжение
перезапускает трек с начала) либо `resume_attempts = 1` +
`resume_escalate_play = false`.
